# Original OS4 themes without offline conversion

Research snapshot: 2026-09-05. Original theme folders can be the source of truth without requiring a PC converter. Images and bitmap fonts already have direct runtime loaders. Original GIF playback has a fallback with correctness and performance limits. Original theme audio is the largest deliberately disabled capability on N64. Removing the converter requirement therefore needs more than the FPGA GIF path.

This is a source audit and proposed test sequence, not a claim that an unconverted theme runs at 60 FPS. No production code or hardware configuration changes accompany this document.

## What the original software expects

OS4 `rtk.py` loads images with pygame, applies its configured color key, reads bitmap font coordinates from CSV-formatted `.dat`, and uses Pillow for animated GIF composition. Backgrounds and transitions use the original GIF files. Animation timing, transparency and disposal must follow this implementation, including its update cadence; decoding faster does not authorize skipping visible animation states. These semantics remain the reference for any FPGA implementation.

OS4 `sound_mgr.py` loads six named theme effects as `.ogg` with default effects as fallback. Music plays through pygame's mixer. `utils.py::load_music` admits **`.mp3`, `.ogg`, `.xm`, `.mod`, `.it`** in the system playlists and theme `sounds/music`. Thus tracker music is part of the source-defined inventory, even though Final Fight uses MP3. General-purpose converter support for more extensions is not evidence that OS4 theme discovery admits them.

## Direct-loading status

| Original asset | Current PhosphorOS path | Conversion requirement and limits |
|---|---|---|
| `theme.ini` | [theme_mgr.c](../../src/mgr/theme_mgr.c) | Parsed directly. Preserve keys, theme paths and immutable source files. No binary theme pack is necessary. |
| BMP images and font atlases | [image_bmp.c](../../src/rtk/image_bmp.c), [text.c](../../src/rtk/text.c) | Direct BMP decoding exists. The loader first tries a native companion, then the original BMP. Supports BI_RGB 1/4/8/16/24/32-bit, RLE8 and 16-bit bitfields, including V4/V5 header handling. A `.sprite` is an optimization, not a mandatory source format. Allocation, dimensions, palette and alpha limits still apply. |
| Font `.dat` | [theme_mgr.c](../../src/mgr/theme_mgr.c), `load_font_map`; [text.c](../../src/rtk/text.c), atlas loading | Read directly with OS4 coordinate and comma-key grammar. These are bitmap atlases plus maps, not TrueType fonts. Conversion cannot supply a missing glyph; atlas/map consistency remains necessary. |
| PNG | [png.c](../../src/rtk/png.c), [image.c](../../src/rtk/image.c) | Runtime streaming decoder exists for common 8-bit channels and 1/2/4/8-bit palette/gray, with palette transparency. Interlaced and 16-bit PNG are unsupported; alpha is reduced to the backend representation. Existing theme names that request BMP do not automatically discover a renamed PNG. |
| Original background/transition GIF | [bg.c](../../src/rtk/bg.c), [sprite.c](../../src/rtk/sprite.c), [image_gif.c](../../src/rtk/image_gif.c), [rtk_gpu_n64.c](../../src/rtk/rtk_gpu_n64.c) | Native fallback exists; `.gif64` is preferred when present. LZW decode and composition are runtime work. Disposal 3 is explicitly unsupported in the current portable decoder. Large N64 CI8 canvases cannot assume arbitrary local palettes fit one composed 256-color palette. Direct-loading existence is not full GIF compatibility or a speed guarantee. |
| Ogg effects | [sound_mgr.c](../../src/mgr/sound_mgr.c) | Portable stb_vorbis decode-to-PCM path exists, but N64 disables CPU codecs. Stock N64 needs supported wav64 effects today. Reusing the PCM path could remove that requirement; memory, preparation latency and concurrent music costs require measurement. |
| Ogg/MP3 music | [snd_ring.c](../../src/mgr/snd_ring.c), [sound_mgr.c](../../src/mgr/sound_mgr.c) | Portable streaming stb_vorbis/minimp3 paths exist. All three N64 defconfigs set `CONFIG_CPU_CODECS := 0`; source selection in `mk/sources.mk` also excludes their decoders. Merely changing file discovery cannot enable playback. |
| XM/MOD/IT music | OS4 inventory versus [sound_mgr.c](../../src/mgr/sound_mgr.c) | Current theme music discovery lacks these formats. The converter's `AUDIO_EXT` also omits them. This is a separate compatibility gap requiring a bounded tracker decoder integration through the sound owner, not a format rename. |
| Other audio extensions | [themeconv.py](../../tools/themeconv/themeconv.py) | The converter accepts WAV, FLAC, AAC and others in addition to Ogg/MP3. This does not establish native theme playback support or an OS4 requirement. Inventory real themes before expanding scope. |

The current converter emits GIF64, native sprites and 44.1 kHz plain-VADPCM wav64, and deletes successfully converted source files. That workflow does not meet the requested unchanged-original-folder experience. No offline conversion is intrinsically required to represent these assets: N64 still needs decoded pixels and PCM or a supported compressed audio stream, but those can be produced at runtime. Efficient production of that representation remains the engineering problem.

## Existing mechanisms to reuse

RTK owns decode, composition, resource retirement and theme cancellation. Keep the portable original-file path and add acceleration through its backend seam. The FPGA must consume original GIF bytes; host-generated packets remain research fixtures only. The current Final Fight pilot is deliberately narrow: global palette, transparent index 255, disposal 0 and no interlace. It does not establish general GIF support. Local palettes, disposal 2/3, interlace, loops, transitions and malformed input need explicit coverage before claiming vanilla-theme compatibility.

The [receiver research](../../tools/verify/sc64-gif/README.md) separates RTL simulation from real N64 packet transfer/application/render tests. Full CI8, changed tiles and row spans trade PI bytes against CPU scatter work. A correct simulated decoder and a passing physical receiver do not establish physical FPGA integration or end-to-end UI FPS; see the [testing ledger](../sc64-ui-testing.md).

The sound owner already feeds PCM through `phos_pcm_source_t` and `snd_ch_play_pcm` in [snd_backend.h](../../src/mgr/snd_backend.h). Its existing N64 backend provides the RSP mixer/native wav64 path. Reuse these interfaces rather than creating a second mixer. RSP mixing/resampling and VADPCM decoding do not themselves decode Ogg Vorbis or MP3. A future DSP/FPGA codec needs separate complexity, memory, contention and audio-fidelity evidence.

Existing N64 GIF caching includes cart memory, resident decoded frames and disposable SD `.gc` data. The SD cache has a 16 MiB guard and identity fields including source path, size, modification time and decoder version. Final Fight's 1,717 full 320×240 CI8 frames alone require 131,865,600 bytes, so a complete uncompressed cache does not fit that guard or 64 MiB cart RAM. Reuse the owner and invalidation rules; do not assume caching the entire animation solves streaming.

## Bounded next steps

1. Establish an **unconverted Final Fight** baseline with the original INI, BMP/DAT, GIF, Ogg effects and MP3 music. Explicitly report skipped audio, decode failures and animation discrepancies. Compare original assets against the current converted baseline without changing theme files or the benchmark epoch.
2. Complete the original-GIF FPGA transport and bounded ownership/cancellation path already under investigation. Test actual board decoding plus music and navigation; retain source-based pixel goldens. Broaden the GIF corpus before advertising support beyond the pilot subset.
3. Test N64 Ogg effects alone using the existing PCM loader, then original MP3 music alone, then both with the GIF path. Record preparation latency, peak heap on 4/8 MiB, CPU service time, underruns and frame timing. Enabling `CONFIG_CPU_CODECS` is an experiment, not a proven optimization; its ring producer currently allows a 9 ms service budget.
4. Inventory the remaining pinned theme archives for real codec variants, GIF disposal/palettes and PNG variants. Add explicit coverage for OS4 tracker music if present, while retaining its known source-level compatibility requirement regardless of Final Fight's contents.
5. Validate source-only image/font loads and transitions through the existing shared primitives. Preserve fallback and missing-file behavior. Remove the user-facing converter requirement only when the original-file paths cover the tested theme corpus; keep historical converted-file reading compatible during migration.

**No PC conversion** means users copy/extract their original OS4 theme folder without running Python or generating replacement assets. An **on-device disposable cache** can also meet that condition, but it is a distinct implementation choice: it consumes first-use time, storage and write bandwidth. It must live outside immutable theme folders, invalidate when sources change, publish only complete validated data, recover after interrupted writes and cancel before the owner releases its destination. On-device wav64 generation additionally needs an encoder; the current native wav64 playback API is not one. None of these cache proposals has a performance acceptance result in this audit.
